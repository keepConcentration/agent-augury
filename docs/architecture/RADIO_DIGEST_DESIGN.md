## 0. 한 줄

승인을 마친 에이전트에게 들어오는 동료의 **순수 표(`APPROVE:`/`READY:`)** 를
전문 대신 한 줄로 접는다. **버리지는 않는다.**

---

## 1. 출발점 — 사용자 제안과 그 수정

원안: *"agent-1이 APPROVE하면 그 이후 메시지는 agent-1의 inbox에 넣지 않음.
`REJECT:` 같은 건 넣는다."*

목표(재우기)는 **이미 달성돼 있다.** D5(`_needs_model_reply`)가 done 에이전트에게
온 동료 표에 대해 **모델을 호출하지 않는다.** `REJECT:` 는 `approvals` 를 비워
done 상태 자체를 풀기 때문에 별도 예외도 필요 없다.

남은 차이는 **배달을 막을 것인가**인데, 막으면 두 가지가 깨진다.

| 문제 | 내용 |
|------|------|
| **깨어날 때 장님** | done 중 오간 논의가 대화에 없으면, REJECT/페이즈 전환으로 깨어난 에이전트가 맥락을 모른다. `read_resource` 로 스레드를 통째로 다시 읽는 편이 더 비싸다 |
| **SSOT 역전** | 배달 대상은 `MessageServer.send_message` 가 정한다. 거기서 거르려면 서버가 프로토콜 done 상태를 알아야 하는데, `DESIGN.md` §3.3 은 **"메시지 서버가 SSOT, 프로토콜은 그 위"** 로 못박는다 |

→ **버리지 말고 접는다.** 배달·보관은 그대로, `[radio]` 로 조립할 때의 분량만 줄인다.
SSOT 를 건드리지 않고 `AgentLoop` 안에서 끝난다.

---

## 2. 측정 (최근 3세션, 실제 체크포인트)

```text
대화 전체   408,175자
  radio     113,401자  (27%)
```

`[radio]` 안을 메시지 종류별로 쪼개면:

| 종류 | 건수 | 글자 | radio 내 비중 |
|------|-----:|-----:|----:|
| `FINAL:` | 35 | 32,194 | **29%** |
| `APPROVE:` | 138 | 26,737 | **24%** |
| `PROPOSE:` | 42 | 15,090 | 13% |
| `READY:` | 36 | 1,377 | 1% |
| `REJECT:` | 3 | 219 | 0% |
| 작업 로그 | 89 | 35,256 | 31% |

시그널 메시지 중앙값은 **110자**인데 최대 **1,345자** — 일부 에이전트가
`APPROVE:` 에 전체 답안을 다시 붙인다.

### 2.1 앞선 추정이 틀렸다

이전에 "APPROVE 포함 블록이 절반"이라 보고 **절반 절감**을 기대했다.
실제로는 대부분의 블록이 시그널과 작업 로그를 **섞어** 담는다 —
순수 시그널만 있는 블록은 **7%** 뿐이다. 따라서 압축은 **블록 단위가 아니라
블록 안 메시지 단위**여야 한다.

## 3. 설계

`AgentLoop.step()` 의 D5 분기(`if self.protocol_done:`)에서 radio 를 조립할 때:

```text
for each drained message:
    APPROVE: / READY:  ->  접는다 (작성자만 수집)
    REJECT: / PROPOSE: / FINAL: / RESULT:  ->  전문 유지
    비시그널(작업 로그)                     ->  전문 유지
```

접힌 것은 한 줄로:

```text
[radio]
(peers signalled: agent-2, agent-3 APPROVE:)
from agent-4: 좌표 재계산 결과 ...   <- 작업 로그는 그대로
```

판정은 **`signals.has_signal` 을 그대로 쓴다** — 장식된 `**APPROVE:**` 도 접히고,
게이트와 판정이 어긋나지 않는다.

### 3.1 왜 `APPROVE:`/`READY:` 만인가

done 에이전트에게 **표는 이미 아는 정보**다 — 누가 승인했는지는 게이트 상태이고
`session.gate` 이벤트에도 실린다. 반면:

- `REJECT:` — done 을 해제한다. 이유를 알아야 한다
- `PROPOSE:` / `FINAL:` — 검토 대상 본문
- `RESULT:` — 동료의 근거
- 작업 로그 — 다음에 깨어났을 때 필요한 맥락

즉 **내용이 있는 것은 전부 남는다.** 접히는 것은 "동의합니다"의 변주뿐이다.

### 3.2 적용 범위

`protocol_done` 인 에이전트에게만. 아직 투표하지 않은 에이전트는 동료의 표를
**읽고 판단해야** 하므로 전문을 받는다.

## 4. 절감 한도 (정직하게)

```text
APPROVE(24%) + READY(1%)  =  radio 의 25%
radio 는 대화의 27%
→ 대화 전체의 약 6%
```

**6%다.** 원안이 겨냥한 모델 호출 절감은 D5 가 이미 가져갔고, 여기서 줄어드는 것은
다음 호출의 프롬프트 분량뿐이다.

### 4.1 같은 크기의 이득이 이미 진행 중이다

`FINAL:` 이 radio 의 **29%**(대화의 8%)인데, 그 35건 중 상당수가 **중복 초안**이다.
`PHASE_ENTRY_SIGNAL_DESIGN` §6b 의 M4a(초안 하나)가 이미 그걸 겨냥하고 있고,
직전 실행에서 `draft_already_posted` 가 8회 발동했다. **코드 추가 없이** M5 와
비슷한 규모를 이미 먹었을 가능성이 크다.

## 5. 결정 — 착수 보류

**설계는 확정하되 구현은 다음 라이브 실행 이후로 미룬다.**

근거:

1. 절감 6%. 조립 경로(hot path)에 분기와 테스트를 새로 넣을 만큼인지 불확실.
2. M4a + 신호 정규화가 `FINAL:` 중복을 실제로 얼마나 줄였는지 **아직 측정되지
   않았다.** 그 결과에 따라 radio 구성이 크게 바뀐다.
3. 접기는 **되돌리기 쉬운 순수 최적화**다. 급할 이유가 없다.

### 5.1 다음 실행에서 볼 것

```bash
# radio 종류별 재측정 (본 문서 §2 와 같은 방식)
FINAL: 이 radio 의 29% -> 몇 %로 떨어졌나
```

- `FINAL:` 이 10% 아래로 내려갔다면 → M4a 로 충분. M5 는 **폐기 후보**.
- 여전히 25% 이상이면 → 중복 초안이 남았다는 뜻. M5 보다 **M4a 의 남은 경쟁 창**
  (§6b.3c 의 `await` 구간)을 먼저 본다.
- `APPROVE:` 가 30% 를 넘어섰다면 → M5 착수.

---

### 5.2 재측정 결과 (세션 `d6bcbc56`, 2026-09-17)

```text
대화 전체   52,065자
  radio      7,724자  (15%)
```

| 종류 | 건수 | 글자 | radio 내 비중 | 직전 |
|------|-----:|-----:|----:|----:|
| `APPROVE:` | 45 | 4,101 | **53%** | 24% |
| 작업 로그 | 59 | 1,492 | 19% | 31% |
| `PROPOSE:` | 9 | 969 | 13% | 13% |
| `READY:` | 15 | 354 | 5% | 1% |
| `FINAL:` | 3 | 201 | **3%** | 29% |

**§5.1 기준 두 개가 동시에 발동했다.**

- `FINAL:` 29% → **3%**. 10% 아래 → *"M4a 로 충분. M5 는 폐기 후보"*.
  서버에 남은 `FINAL:` 메시지는 **정확히 1건**이다(직전 3세션 35건).
  M4a first-writer-wins 가 의도대로 작동했다.
- `APPROVE:` 24% → **53%**. 30% 초과 → *"M5 착수"*.

### 5.3 그래도 착수하지 않는다

기준은 발동했지만 **표본이 대표성이 없다.**

1. 이 세션의 질문은 `72 - [18 × (7-3) - 24÷6] + 15×2` 한 줄이다. 작업 로그가
   거의 없으니 `APPROVE:` 비중이 자동으로 부풀었다 (작업 로그 31% → 19%).
2. 절대 절감은 여전히 **4,101 / 52,065 ≈ 8%** 로 §4 의 6% 와 같은 자리수다.
3. **M4c(§6b.6, `PHASE_ENTRY_SIGNAL_DESIGN`)가 방금 표 자체를 줄였다** —
   게이트마다 초안 작성자의 왕복이 사라져 16표 → 12표(25% 감소). 여기서도
   "코드 없이 M5 만큼 먹는" 일이 반복될 수 있다.

**따라서 판정 보류를 한 번 더 연장한다.** 다음 측정은 **작업 로그가 실제로
쌓이는 과제**(코드 읽기·다단계 조사 등)에서 한다. 산수 문제로는 이 결정을
내릴 수 없다.

## 7. 요약

사용자 제안의 목표(재우기)는 **D5 가 이미 달성**했다. 남은 것은 분량이고,
**버리지 말고 접는** 방식이면 장님·SSOT 문제 없이 줄일 수 있다.
다만 측정된 절감이 **6%** 이고, 같은 크기를 M4a 가 코드 없이 가져갔을 수 있어
**다음 실행의 재측정 후 착수 여부를 정한다.**
