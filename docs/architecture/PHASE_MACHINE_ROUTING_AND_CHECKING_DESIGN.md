## 1. 왜 한 문서인가

| 논문 | 주장 | 우리 자리 |
|------|------|-----------|
| 2609.13890 | 협업 이득은 난이도에 비례(2.4→21.1점)하는데 비용은 내내 10배. **문제마다 토폴로지를 골라라** | `next_phase_after_gate(P2_SPLIT)` |
| 2609.17527 §L4 | 협업 규범을 계약으로 쓰고 **liveness·safety·efficiency 를 분석할 수 있게** 하라 | `_valid_transitions` + 게이트 상태 |

**두 인용 모두 "구현"이 아니라 "차용"이다.**

- 13890 은 **문제를 시작하기 전** 토폴로지를 고른다. 우리는 **P2 가 끝난 뒤**
  남은 페이즈를 접는다. **같은 직관, 다른 시점** — 그래서 절감 상한도 다르다
  (§2.5).
- 17527 §L4 는 **다자·다원 신뢰**의 사회 harness 다(발언권 배분, 기아 방지).
  우리는 **단일 신뢰 도메인**의 페이즈 머신이다. 가져오는 것은 L4 의 메커니즘이
  아니라 **"규범을 분석 가능한 형태로 두라"는 요구**뿐이다.

둘 다 **같은 함수 두 개**를 건드린다. 그리고 미결로 남은 **D12**(전원 park 시 턴이
안 끝남)도 R2 가 답을 내야 하는 질문이다. 그래서 묶는다.

## 2. R1 — P2 가 "분할 없음"이라고 하면 P5 로 바로 간다

### 2.1 측정 — 에이전트가 이미 말하고 있었다

체크포인트 전 세션을 훑으니 **6개 세션**에서 P2 의 `PROPOSE:`/`APPROVE:` 가
분할 불필요를 명시했다.

```text
d6bcbc56  "이 문제는 단순 계산이므로 세부 질문 분할이 필요 없습니다"
e6580d5a  "PROPOSE: 이미 계산이 완료된 단순 수식 문제이므로, 추가 분할 작업은 불필요합니다"
f0eb6ad1  "PROPOSE: 분할할 하위 질문이 없습니다. ... 검증/리뷰 단계로"
dc79a366  "분담이 필요 없는 수준이므로 빠르게 진행하겠습니다"
d6bcbc56  "APPROVE: ... 분할할 작업이 없습니다. P3로 진행합니다"
157f6dae  "- 추가 분할 작업 불필요"
```

**그러고도 프로토콜이 P3·P4 로 행진시켰다.** 그 구간의 비용:

| 세션 | 전체 | P2 | **P3+P4** | P5 | P3+P4 비중 |
|------|-----:|---:|------:|---:|----:|
| `d6bcbc56` | 29 | 7 | **11** | 5 | 38% |
| `dc79a366` | 29 | 8 | **11** | 5 | 38% |
| `e6580d5a` | 37 | 8 | **12** | 9 | 32% |
| `f0eb6ad1` | 50 | 8 | **22** | 14 | 44% |

그 11~22 메시지가 만든 정확도 개선은 **0** 이다 — 네 에이전트 모두 **P1 에서
이미 같은 정답**을 냈다(107/3, 34, 222, 138).

반대로 BSD 증명 요청(`ffb70b4b`)에서는 P4 가 **Gross-Zagier 공식의 분모 누락**을
잡고 P2 가 **존재하지 않는 `agent-5` 배정**을 막았다. **협업이 값을 한 것은
어려운 문제에서였다** — 논문의 결론과 같다.

### 2.2 신호 — 추론이 아니라 선언이어야 한다

**rev.1 은 빈 `_assignments` 를 신호로 쓰려 했다. 측정해 보니 틀렸다.**

§2.1 의 여섯 세션에서 체크포인트의 `assignments` 를 그대로 읽으면:

| 세션 | 산문으로 "분할 불필요"? | `assignments` | rev.1 이 발동? |
|------|:---:|---:|:---:|
| `d6bcbc56` | ✓ | 0 | ✅ |
| `e6580d5a` | ✓ | 0 | ✅ |
| `f0eb6ad1` | ✓ | 0 | ✅ |
| `dc79a366` | ✓ | **4** | ❌ |
| `157f6dae` | ✓ | **4** | ❌ |
| `63fec483` | ✓ | **4** | ❌ |

**절반이다.** 라우팅 신호로 쓸 수 없는 정확도다.

놓친 셋이 왜 놓쳤는지가 결정적이다. `157f6dae` 의 분담은 이렇다.

```text
ASSIGN agent-1: 계산 결과 도출 (풀이 과정 포함)
ASSIGN agent-2: 계산 결과 도출 (풀이 과정 포함)
ASSIGN agent-3: 계산 결과 도출 (풀이 과정 포함)
ASSIGN agent-4: 계산 결과 도출 (풀이 과정 포함) + 전체 결과 검증 및 제출
```

**넷이 똑같은 일을 배정받았다.** 형식은 분담이고 실질은 분담이 아니다.
`dc79a366`·`63fec483` 도 "풀이 검토" / "답안 형식 확인" 처럼 **이미 나온 답에
붙인 검토 역할**이다.

**즉 `ASSIGN` 은 진짜 분담과 형식적 분담을 구별하지 못한다.** 빈 딕셔너리는
"분할 불필요"의 한 표현일 뿐이고, 팀은 그것을 산문으로 쓰거나 형식으로 채우거나
자유롭게 한다.

#### 고치는 방향 — 선언을 요구한다

문자열을 비교해 "네 배정이 같으면 분할 아님"을 판정하는 길이 있지만, 그것은
`DESIGN` 이 금지한 NLP 휴리스틱이다(§2.6). 그리고 `dc79a366` 처럼 문자열이
실제로 다른 경우는 못 잡는다.

**프로토콜의 나머지가 전부 명시 신호다** — `READY:`, `PROPOSE:`, `APPROVE:`,
`ASSIGN`, `SUBMITTER:`. 라우팅만 추론에 기대는 것이 일관성 없다.

```text
PROPOSE:
SPLIT: none          <- 새 선언. "나눌 것이 없다"
SUBMITTER: agent-3
```

- `assignments.py` 가 이미 `parse_assignments` / `parse_submitter` 를 정규식으로
  갖고 있다. `parse_split` 한 개를 같은 자리에 더한다.
- P2 프롬프트에 한 줄: *분할이 필요 없다고 판단하면 `SPLIT: none` 을 쓰라.*
- **판정은 선언에만 의존한다.** 빈 `_assignments` 는 라우팅에 쓰지 않는다 —
  ASSIGN 을 잊은 것과 분할이 불필요한 것은 다른 사건이다.

#### 대가

선언이므로 **팀이 안 쓰면 아무 일도 일어나지 않는다**(현재 동작 = P3 로 진행).
안전한 실패다. 반대로 남용하면 어려운 문제에서 P3·P4 를 건너뛰는데, 그때도
P5 의 `FINAL:` + 전원 승인은 남으므로 **검토가 0이 되지는 않는다**(§2.4).

### 2.3 인접 버그 — `_assignments` 는 "이긴 초안"의 것이 아니다

**rev.2 에서 R1 의 선행 조건은 아니게 됐다**(라우팅이 `SPLIT:` 선언만 보므로).
그래도 **지금 버그다** — `_assignments` 는 프롬프트의 *"Your assigned share"*
줄로 에이전트에게 나가고, 틀리면 엉뚱한 몫을 시킨다.

지금 `_on_message` 는 **P2 의 모든
`PROPOSE:`** 에서 ASSIGN 을 파싱한다 — 게이트가 **무시한 경쟁 초안**까지.

```python
if self.phase == P2_SPLIT and has_signal(content, "PROPOSE:"):
    found = parse_assignments(content, self.participants)
    if found:
        self._assignments = found      # 누가 쓴 것인지 안 본다
```

`ConsensusGate` 는 `draft_author` 가 아닌 초안을 **전부 버리는데**(M4a),
`_assignments` 는 마지막에 도착한 것을 받는다. 즉 **런타임이 기록한 분담이
팀이 승인한 분담과 다를 수 있다.**

이것은 이미 한 번 관측됐다 — `dc79a366` seq 8 의 유령 분담안
(`PHASE_ENTRY_SIGNAL_DESIGN` §6b.14). 그때는 신호가 묻혀서 **우연히** 무사했다.

**수정:** 초안 소유자의 것만 받는다.

```python
if self.phase == P2_SPLIT and has_signal(content, "PROPOSE:"):
    gate = self._gates.get(P2_SPLIT)
    author = message.get("author", "")
    if gate is not None and gate.draft_author not in (None, author):
        return                          # 경쟁 초안: 게이트와 같이 무시
```

`if found:` 도 손봐야 한다 — 같은 작성자의 **재초안에 ASSIGN 이 없으면**
지난 분담이 그대로 남는다. 초안이 바뀌면 분담도 그 초안의 것이어야 한다.

### 2.4 전이 허용

`_valid_transitions` 는 full 모드에서 `P2_SPLIT: {P3_EXECUTE, REJECTED}` 다.
P2 → P5 는 **거부된다.**

```python
# full 모드
P2_SPLIT: {P3_EXECUTE, P5_SUBMIT, REJECTED},     # P5 추가
```

전이를 안 열면 **게이트 open 콜백 경로에서 터진다.** 라우팅과 전이는 한
덩어리로 묶어야 한다.

```text
ConsensusGate 열림
  -> _handle_gate_open(P2_SPLIT)
  -> _on_protocol_gate_open(session, P2_SPLIT)          # session.py:1718
  -> next_phase = protocol.next_phase_after_gate(P2_SPLIT)   # P5 를 돌려주면
  -> protocol.advance(P5_SUBMIT)                        # 여기서 ValueError
```

즉 **§2.4 의 전이 추가 + 라우팅 + `advance` 경로 테스트**가 한 변경이다.
전이만 빠지면 *"게이트는 열렸는데 세션이 예외로 죽는다"* 가 된다.

라우팅 자체는 한 곳:

```python
def next_phase_after_gate(self, phase):
    if self.mode == "light":
        return COMPLETED if phase == P5_SUBMIT else None
    if phase == P2_SPLIT and self.split_declared_none:
        # 팀이 SPLIT: none 을 선언했다. P3 는 각자 자기 몫을 하는 단계이고
        # P4 는 그 결과를 대조하는 단계이므로, 몫이 없으면 둘 다 빈 단계다.
        return P5_SUBMIT
    return {...}.get(phase)
```

**P4 를 건너뛰는 것이 맞는가.** P4 는 "각자 결과를 근거와 함께 방송"이다.
P3 를 건너뛰면 대조할 결과가 없다. 그리고 P5 는 `FINAL:` 초안 + 전원 승인이므로
**검토 자체는 사라지지 않는다** — 초안 하나를 셋이 읽는 형태로 남는다.

### 2.5 절감 상한 — 논문보다 적게 아낀다

13890 은 **호출 전에** 토폴로지를 고르므로 Single 을 고르면 1.0× 만 쓴다.
우리는 **P1 과 P2 를 이미 치른 뒤** 결정한다.

```text
논문:            결정 -> [고른 토폴로지만 실행]
agent-augury:    P1 + P2 실행 -> 결정 -> [P3·P4 생략] -> P5
```

§2.1 표로 환산하면 아낄 수 있는 것은 **P3+P4 구간(전체의 32~44%)** 이고,
P1·P2 는 그대로 낸다. **논문의 "40% 비용" 같은 숫자는 우리 구조에서 나오지
않는다.** 이 차이를 숨기지 않는 것이 리뷰를 견디는 길이다.

더 앞에서 고르려면 첫 턴 `mode` 를 질문 보고 정해야 하는데, 그것이 바로
논문의 정적 예측기이고 우리가 안 하기로 한 것이다(§2.6).

### 2.6 안 가져오는 것

| 논문 요소 | 왜 안 쓰나 |
|-----------|-----------|
| 학습된 예측기 (graph net) | (문제, 토폴로지, 성공) 라벨 데이터셋이 필요하다. 우리에겐 벤치마크가 없고 만드는 것은 별도 연구다 |
| 39개 특징 / TF-IDF | 진술문에서 **짐작**하는 것. 우리는 P2 뒤에 팀의 **선언**을 받는다 (대가는 §2.5) |
| 배정 문자열 비교 휴리스틱 | "넷이 같은 배정이면 분할 아님" 은 `157f6dae` 는 잡고 `dc79a366` 는 못 잡는다. NLP 금지 원칙 위반이고 정확도도 부분적 |

| 비용 기반 최적화 | 우리 `usage` 누적이 아직 상한으로 쓰이지 않는다. 별개 항목 |

## 3. R2 — 페이즈 기계를 실행 전에 검사한다

### 3.1 지금까지 버그를 어떻게 찾았나

**전부 라이브 실행에서 사람이 멈춘 것을 보고서였다.**

| 버그 | 발견 경로 | 커밋 |
|------|-----------|------|
| P2 park 교착 (전원 APPROVE, 아무도 PROPOSE 못 함) | 체크포인트 사후 분석 | `0975acf` 계열 |
| 초안 작성자가 자기 표를 기다림 | `d6bcbc56` 에서 사람이 찔러야 함 | `0b80ff6` |
| 넛지가 P1 `READY:` 를 못 봄 | `43addf1b` 에서 3/4 정지 | `a6ffecd` |
| 게이트 열린 뒤 초안 추가 | `ffb70b4b` seq 38 | `374ce12` |
| 보고서 꼬리의 신호 | `dc79a366` 에서 사람이 찔러야 함 | `893166a` |
| **전원 park 무한대기 (D12)** | **아직 미해결** | — |

**라이브 실행 한 번에 버그 하나씩 사고 있다.** 논문 L4 가 말하는 것이 정확히
이 낭비다 — 규범을 계약으로 쓰고 **liveness 를 분석**하라.

### 3.2 상태 공간이 작다

```text
phase          : P1 | P2 | P3 | P4 | P5 | COMPLETED | REJECTED     (7)
게이트마다     : approvals ⊆ participants                          (2^N)
                 draft_author ∈ participants ∪ {None}              (N+1)
                 proposal_received ∈ {T, F}                        (2)
                 opened ∈ {T, F}                                   (2)
ready_states   : ⊆ participants                                    (2^N)
```

N=4, **활성 게이트 하나만 세면** 게이트당 약 1,600. 전이는 에이전트 행동
6종(`READY / PROPOSE / APPROVE / REJECT / FINAL / park`) × N.

**다만 이 1,600 은 낙관적인 숫자다.** 빠진 것들:

| 빠진 축 | 영향 |
|---------|------|
| 게이트 4개가 **동시에 바인드돼 있다** | 비활성 게이트도 상태를 갖는다(REJECT 후 재진입 시 되살아남) |
| `human_pending` | `await_human_after_agents` 게이트마다 ×2 |
| `REJECT:` 순환 | 상태 수보다 **경로 길이**가 폭발한다 — BFS 는 상태로 접지만 순환이 깊으면 느려진다 |
| `opened` ↔ `approvals` 상관 | 독립이 아니어서 실제 도달 상태는 곱보다 적다(유리한 방향) |

→ **"완전 탐색이 가능하다"고 단정하지 않는다.** N=3 에서 먼저 재고(E4),
느리면 활성 게이트만 모델링하거나 순환 깊이를 제한한다. 그래도 TLA+ 같은
새 도구를 들이기 전에 시도할 값은 충분히 싸다.

### 3.3 불변식 — 과거 버그가 어긴 것들

| # | 불변식 | 어긴 버그 |
|---|--------|-----------|
| **S1** | 제출된 답은 **전원 승인을 받은 그 초안**이다 | 게이트 열린 뒤 초안 추가 (`374ce12`) |
| **S2** | 게이트는 **현재 초안에 대한** N개의 서로 다른 표로만 열린다 | 초안 없는 표를 세던 것 (D10) |
| **S3** | 런타임이 기록한 분담 = 승인된 초안의 분담 | **§2.3 — 아직 어기는 중** |
| **L1** | 도달 가능한 모든 상태에서, 어떤 에이전트 행동열이 COMPLETED 로 간다 | P2 park 교착, 작성자 미투표 |
| **L2** | 모든 에이전트가 park 이면 그 상태는 종단이다 | **D12 — 아직 어기는 중** |

S3 와 L2 는 **지금 코드가 어기고 있다.** 모델 체킹을 붙이면 라이브 실행 없이
드러난다.

### 3.4 구현 — pytest 안의 BFS

새 의존성도, 새 언어도 쓰지 않는다.

```python
# tests/test_phase_machine_invariants.py  (스케치)
def test_no_deadlock_reachable():
    """모든 도달 상태에서 COMPLETED 로 가는 길이 있는가."""
    seen, stuck = set(), []
    frontier = [initial_state(n=3)]
    while frontier:
        s = frontier.pop()
        if s in seen:
            continue
        seen.add(s)
        nxt = [apply(s, a) for a in legal_actions(s)]
        if not nxt and not is_terminal(s):
            stuck.append(s)
        frontier.extend(nxt)
    assert not stuck, stuck[:3]
```

- **N=3 으로 돈다.** N=4 도 되지만 3 이면 모든 버그 유형이 재현되고 빠르다.
- **실제 객체를 쓴다** — `ConsensusGate` / `CollaborationProtocol` 을 그대로
  구동해 모델과 코드가 갈라지지 않게 한다. 별도 모델을 쓰면 그 모델이
  낡는 것이 다음 버그가 된다.
- `park` 을 행동으로 넣어야 L2(D12)가 잡힌다.

### 3.5 기대치를 낮게 유지한다

이것은 **프로토콜 계층만** 검사한다. 범위 밖:

| 밖에 있는 것 | 예 (전부 실제로 일어난 것) |
|--------------|---------------------------|
| 툴 계층 소프트 차단 | `signal_not_first`, `gate_already_open` |
| 모델의 말버릇 | `APPROVE:` 를 답변 텍스트에만 씀, 보고서 꼬리에 붙임, `PROAPPROVE:` |
| 메시지 도착 순서·경쟁 | `draft_author` 낡은 스냅샷, 승인 뒤 `FINAL:` |
| 세션 루프 | park/wakeup 타이밍, `max_steps` |

**즉 L1 이 초록이어도 라이브 교착은 남을 수 있다.** 오늘까지 고친 버그 5개 중
BFS 가 잡을 수 있었을 것은 **2개**(P2 park 교착, 작성자 미투표)뿐이다. 나머지
셋은 툴 계층이거나 경쟁이었다.

그래도 값을 하는 이유는 **회귀 방어**다. 그 2개는 라이브 실행 두 번을 샀고,
BFS 가 있으면 0원이다. 그리고 **D12(L2)는 BFS 가 잡을 수 있는 쪽**이다.

## 4. D12 는 R2 가 결판낸다

D12: **전원이 park 하면 턴이 끝나지 않는다.** `_wait_for_gate_wakeup` 에
생존성 검사가 없고, docstring 이 그것을 **의도**라고 적어 두었다.

```text
Does not end the turn merely because every agent is idle.
```

의도인 이유는 **사람이 게이트를 깨워 주는 창**이다. 실사용에서 사용자가
*"@agent-4 approve 너만 남았어"* 로 세 번 구해 줬다.

불변식 L2 를 쓰면 질문이 명확해진다.

| 안 | L2 | 사람 구조 창 | 평가 |
|----|----|-----------|------|
| 그대로 | ✗ 위반 | ✓ | 헤드리스 실행이 영구 정지 |
| 전원 park → 턴 종료 | ✓ | ✗ | 구조 창 소멸 |
| **전원 park → 턴 종료, 단 interact 서피스가 붙어 있으면 대기** | ✓ | ✓ | **후보** |

세 번째가 맞아 보인다. 세션은 이미 interact 서피스 부착 여부를 안다
(`_human_approval_needs_interact` 계열). **다만 이것은 R2 의 결론으로
정하는 것이 맞다** — 불변식을 먼저 쓰고, 그것이 요구하는 것을 고친다.

## 5. 인접하지만 여기 아닌 것 — 승인자에게 동료 표를 가릴 것인가

**rev.1 은 이것을 2609.17527 §L3 인용으로 적었다. 인용이 틀렸다.**

§L3(Personal Firewalls)은 **신뢰·정책으로 받은 메시지를 선별**하는 것이고,
격리 컨텍스트는 거기서 **프롬프트 주입 방어** 용도다. 내가 원하는 것은
"승인자가 동료 표를 못 보게 해 독립적으로 판단하게 한다"인데, 그것은 L3 이
아니라 논문의 **실험 설정 E1 의 isolated sessions** 에 가깝다.

**그리고 논문은 그 격리가 해로웠다고 보고한다.**

```text
S2(그룹 미팅): isolated sessions -> M2 는 N>1 에서 성공률 0%
                shared sessions  -> 80~90%
```

즉 **논문을 근거로 격리를 주장할 수 없다.** 문제는 실재하지만(아래) 해법은
우리가 따로 증명해야 한다.

관측된 승인 연극:

```text
seq 35 agent-1: "3. 전체적 구조: 10개 섹체의 구성이 논리적이고 완전합니다."
seq 37 agent-4: "3. 전체적 구조: 10개 섹션의 구성이 논리적이고 완전합니다."
                                    ^ 오타만 고쳐 그대로 베낌
```

승인자의 `[radio]` 에 **동료의 승인문이 들어 있어서** 베낄 수 있었다. 승인 시
동료 표를 가리면 베낄 재료가 없다.

**여기 넣지 않는 이유 셋:**

1. 페이즈 전이 기계가 아니라 `[radio]` 조립(`AgentLoop.step`)의 문제다.
2. 가리면 **반대 손실**이 있다 — 동료의 `REJECT:` 이유를 못 본다.
3. **논문이 격리 쪽에 불리한 숫자를 갖고 있다**(위 0% vs 80~90%). 우리 맥락이
   달라도(단일 신뢰 도메인, 산술 아닌 검토) 무시할 근거가 없다.

→ 별도 문서. 그때 필요한 것은 논문 인용이 아니라 **A/B 측정**이다 —
같은 초안을 표 보이는 승인자와 안 보이는 승인자에게 주고 지적 건수를 센다.

## 7. 착수 순서

| 순서 | 내용 | 얻는 것 | 실패해도 |
|------|------|---------|----------|
| 1 | **R2 BFS** (S1·S2·L1) | 과거 버그 2개의 회귀 방어망 | **테스트만 추가** — 동작 변경 0 |
| 2 | **§2.3 분담 소유자** | 프롬프트가 승인 안 된 몫을 시키는 것 제거 | 독립 버그 수정 |
| 3 | **L2 + D12** | 헤드리스 영구 정지 해소 | `has_interact_surface()` 로 값이 싸졌다 (E5) |
| 4 | **R1 라우팅** | P3+P4 구간(32~44%) 절감 | `next_phase_after_gate` 되돌림 |

**1번이 먼저인 이유:** 동작을 하나도 바꾸지 않으면서 그 뒤 세 개의 안전망이
된다. 특히 4번이 새 교착을 만드는지 **붙이는 즉시** 안다.

**rev.1 은 §2.3 을 1번에 뒀다.** R1 의 판정 재료였기 때문인데, rev.2 에서
라우팅이 `SPLIT:` 선언만 보게 되어 **선후 의존이 끊겼다**. 그래도 버그는
버그이므로 2번에 남긴다.

**4번이 마지막인 이유:** 새 신호(`SPLIT:`) + 프롬프트 + 파서 + 전이 + 테스트로
표면이 가장 넓다. 그리고 유일하게 **답의 품질을 바꿀 수 있는** 변경이다.


## 8. 요약

두 논문이 가리키는 곳이 같다 — **페이즈 전이 기계**. 하나는 **쓰지 않아도 되는
페이즈를 쓰고 있다**(측정: P3+P4 가 전체의 32~44%, 정확도 개선 0), 다른 하나는
**교착을 라이브 실행으로 사고 있다**(버그 5개, 전부 실행 후 발견).

우리 답은 둘 다 논문보다 작고, **둘 다 논문의 "구현"이 아니라 "차용"이다**
(§1) — 13890 은 시작 전에 고르고 우리는 P2 뒤에 접으며(절감 상한이 다르다, §2.5),
17527 §L4 는 다자 신뢰의 사회 harness 이고 우리는 단일 신뢰 도메인이다.

### rev.2 에서 바뀐 것

**R1 의 신호가 틀렸다.** rev.1 은 빈 `_assignments` 를 "분할 불필요"로 읽으려
했는데, 같은 여섯 세션을 다시 재니 **절반(3/6)에서만 맞았다**(§2.2). 팀이
`ASSIGN` 을 형식으로 채우기 때문이다 — `157f6dae` 는 **넷에게 똑같은 일**을
배정해 두고 "분할 불필요"라고 썼다.

→ 추론을 버리고 **`SPLIT: none` 선언**을 받는다. 프로토콜의 나머지가 전부
명시 신호인데 라우팅만 추론에 기대는 것이 애초에 일관성 없었다.

**BFS 의 사정거리도 좁혔다.** 오늘까지 고친 버그 5개 중 BFS 가 잡을 수 있었을
것은 **2개**뿐이다(§3.5). 나머지 셋은 툴 계층이거나 메시지 경쟁이다.
그래도 그 2개가 라이브 실행 두 번을 샀고, **D12 는 BFS 가 잡는 쪽**이다.

**§5 의 논문 인용을 고쳤다.** "승인자에게 동료 표를 가린다"는 §L3(방화벽)이
아니라 실험 설정 E1 의 isolated sessions 에 해당하고, **논문은 그 격리가
해로웠다고 보고한다**(0% vs 80~90%). 문제는 실재하지만 해법은 우리가 따로
측정해야 한다.

### 남은 것

착수는 **동작을 안 바꾸는 것부터**다 — BFS(안전망) → 분담 소유자(독립 버그)
→ D12(`has_interact_surface()` 로 값이 싸졌다) → R1(표면이 가장 넓고, 유일하게
답의 품질을 바꿀 수 있다).
